# v0.7 设计笔记：Reviewer 改造（暂缓执行，先存档）

状态：**设计完成，未实施**（2026-08-03 决定先保留记录不开跑）。
证据基础：v0.6 测评（`eval/REPORT-v0.6.md`），270 次官方判分运行。

## 诊断

Reviewer 的两个通道表现完全不同：

| 通道 | v0.6 战绩 | 处置 |
|---|---|---|
| 接受通道（accept → 声称） | 7/7 全真，0 说谎 | 保留 |
| 否决通道（终审 veto） | 35 杀对 / 32 冤杀 = 52%；test 集 47%（低于抛硬币） | 废除其湮灭权 |

机制：能走到终审的补丁已过测试验证（62% 本来就是对的），
"宁可错杀"的门卫在这个池子里杀掉的必然多数是好补丁。
其否决理由以假设性风险为主（实录：xarray-7233 被驳回时 Reviewer 自认
issue_addressed=true、scope_minimal=true，仍以 tests_sufficient=false +
"可能导致/或许引起"式风险否决实测通过的补丁）。

## 三个改动（按优先级）

1. **三态化**：裁决 = 确认 / 有保留 / 否决。任何裁决不再湮灭补丁与结论，
   变为分诊标签。`确认`档保持 0 说谎；`有保留`档进人工复查队列
   （按 v0.6 重放约 67 份、~48% 为真——明码标价的复查清单）。
   纸面收益：声称覆盖 7/62 → 39/62，零推理成本。
2. **只准实证否决**：打"否决"必须引用观察到的事实（跑红的测试 / 真实回归 /
   补丁打不上）；假设性风险只能进备注，无权改变裁决。
3. **一次取证机会**：Reviewer 可点名跑一次 scoped 测试验证怀疑，
   跑不红不许否——"我担心"必须变成"我测了"。

## 验证方案（约一晚、~$8，未执行）

  （动了=改漏到能力层）；否决通道精确率 >75%。
